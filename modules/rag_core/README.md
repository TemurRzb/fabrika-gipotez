# rag_core

База знаний / RAG-ядро: чанкинг, эмбеддинги, векторный поиск, извлечение сущностей.

**Вход:** `query` (см. `retrieval_result.schema.json` -> `query`) + список документов (`document.schema.json`).
**Выход должен соответствовать** [`schemas/retrieval_result.schema.json`](../../schemas/retrieval_result.schema.json).

## Статус: реальные эмбеддинги, не мок

Функция `retrieve(query: dict, documents: list[dict]) -> dict` в [`retrieve.py`](retrieve.py):
- **чанкинг** — группировка строк секции до целевого размера (`_CHUNK_TARGET_CHARS = 600` символов), с попыткой сначала разбить по настоящим абзацам (пустая строка);
- **похожесть** — реальные семантические эмбеддинги, `intfloat/multilingual-e5-small` через `sentence-transformers`, полностью локально (без Yandex API — доступ к нему закрыт для проекта, см. решение перейти на локальные модели);
- **кэш эмбеддингов** — двухуровневый: на диске (`data/embedding_cache.npz`, коммитится в git) и в памяти процесса; пересчитываются только новые/ещё не встречавшиеся тексты;
- `entities` — по-прежнему примитивный regex по числам с единицами измерения (%, мкм, г/л, г/т, pH...);
- `graph_context` всегда пустой.

`get_embedding_model()` — публичная функция, отдаёт ту же загруженную модель, что использует `retrieve()`. Переиспользуется в [`modules/ranking/rank.py`](../ranking/rank.py) для оценки семантической новизны гипотез вместо отдельной модели/эмбеддингов — не плодим лишних загрузок.

## Важные находки на реальных данных (31 документ из `data/parsed_documents/`)

1. **Наивный чанкинг по одиночным строкам душит производительность.** Первая версия (по образцу мока) била текст на чанки по каждому переводу строки — на OCR-тексте (где Tesseract отдаёт практически одну строку на элемент, без пустых строк-абзацев) это дало **~27 000 чанков по ~80 символов** вместо разумных нескольких сотен полноценных абзацев. Текущая группировка по целевому размеру сокращает это до **~2 863 чанков** (~10x).
2. **Железо — узкое место, не код.** Даже после сокращения числа чанков полный пересчёт эмбеддингов занимал **~575 секунд** на разработческом ноутбуке (Intel i3-8145U, 2 физических ядра, без GPU — `torch.get_num_threads()` возвращает 2). Модель и код в порядке, просто CPU слабый.
3. **Решение — дисковый кэш, посчитанный один раз.** `data/embedding_cache.npz` уже посчитан и закоммичен в git для всей реальной базы знаний. После этого повторный вызов `retrieve()` на том же корпусе занимает **~8 секунд** (в 72 раза быстрее) — тестировали в свежем процессе, не за счёт кэша в памяти. Судьи/участники, клонирующие репозиторий, получат мгновенный поиск по существующей базе; пересчитываться будут только по-настоящему новые документы (загруженные через UI).
4. **Качество ощутимо лучше TF-IDF.** Топ-5 результатов на запрос "повысить извлечение золота из упорных сульфидных руд при цианировании" — реальные абзацы именно про цианирование упорных/сульфидных руд, схожесть 0.90+. TF-IDF находил только по точному совпадению слов; E5 — по смыслу.

## MVP на случай нехватки времени

Уже не нужен — реальные эмбеддинги подключены и работают быстро благодаря предпосчитанному кэшу. Если кэш `data/embedding_cache.npz` вдруг отсутствует (например, свежий чекаут без него) — `retrieve()` продолжит работать корректно, просто первый вызов на реальной базе будет медленным (минуты); дальнейшие — быстрыми, кэш досчитается и сохранится сам.

## Рекомендованные библиотеки

- `sentence-transformers` — эмбеддинги (уже используется), при первом запуске скачивает модель `intfloat/multilingual-e5-small` (~470 МБ) с HuggingFace
- `numpy` — хранение/загрузка кэша эмбеддингов, векторные операции
- `scikit-learn` (cosine_similarity) — уже используется

## Как тестировать независимо

```bash
pip install -r requirements.txt
pytest modules/rag_core/tests/test_rag_core.py -v

# ручной прогон на мок-документах
python modules/rag_core/retrieve.py "Повысить извлечение золота при цианировании упорных хвостов на 15%"
```

Первый запуск (в т.ч. первый прогон тестов) будет медленнее — скачивается модель и/или считаются эмбеддинги для текстов, которых ещё нет в `data/embedding_cache.npz`. Для реальной базы знаний (`data/parsed_documents/`) кэш уже посчитан и закоммичен, повторные запуски — секунды.

### Если видите ошибки `HTTP Error 429` от HuggingFace Hub

`sentence-transformers` при каждой загрузке модели делает лёгкий сетевой запрос на проверку обновлений, даже если файлы уже в локальном кэше. В GitHub Codespaces (общие IP-адреса) это иногда упирается в лимит анонимных запросов. Не фатально (веса всё равно загружаются из кэша), но долго ждать ретраи. Два варианта ускорить:

```bash
# если модель уже точно скачана в этом окружении раньше — полностью офлайн:
export HF_HUB_OFFLINE=1

# если это первая загрузка и лимит мешает — аутентифицированные запросы:
export HF_TOKEN=<токен с huggingface.co, Settings -> Access Tokens>
```
