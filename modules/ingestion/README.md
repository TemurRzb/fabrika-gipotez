# ingestion

Приём и предобработка данных: парсинг xlsx/docx/pdf/png, OCR сканов, нормализация метаданных.

**Выход должен соответствовать** [`schemas/document.schema.json`](../../schemas/document.schema.json).

## Статус скелета

| Формат | Статус |
|---|---|
| `.docx` | работает (`python-docx`) |
| `.pdf` с текстовым слоем | работает (`pdfplumber`); автоматически определяет и обходит битые метаданные ширины глифов (см. ниже) |
| `.pdf`-сканы/фото (нет текстового слоя) | работает: `pypdfium2` рендерит страницу в картинку, `pytesseract`/Tesseract распознаёт текст |
| `.png`/`.jpg` (схемы, регламенты, сканы) | работает через OCR (`pytesseract`) |
| `.xlsx` | работает (`openpyxl`) — каждый лист -> одна таблица в `tables[]` |

Функция `ingest(file_path: str, max_pages: int | None = None) -> dict` в [`ingest.py`](ingest.py) — точка входа для одного файла. `max_pages` полезен для быстрой проверки на больших сканированных pdf (полный OCR книги на несколько сотен страниц может быть долгим).

### Пакетная обработка папки с кэшированием: `ingest_folder`

`ingest_folder(folder_path: str, cache_dir: str = "data/parsed_documents", max_pages=None) -> list[dict]` рекурсивно обходит папку и парсит все поддерживаемые файлы (docx/pdf/xlsx/png/jpg), **кэшируя результат на диске** — по одному JSON-файлу на исходный документ в `cache_dir`. Ключ кэша строится из пути+времени изменения+размера файла (без чтения содержимого), поэтому:
- если исходный файл не менялся — результат берётся из кэша, парсинг/OCR не повторяется;
- если файл изменился (или это первый запуск) — файл парсится заново и кэш обновляется.

Это важно, потому что OCR больших сканов — не мгновенная операция: без кэша каждый повторный прогон всего пайплайна на реальной базе знаний заново распознавал бы все сканы. `cache_dir` по умолчанию — `data/parsed_documents/` (в `.gitignore`, не версионируется — это производные данные, а не источник истины).

Временные Excel-локи (`~$...`) и неподдерживаемые форматы пропускаются молча; ошибки парсинга отдельных файлов не прерывают обработку остальной папки (печатаются в stderr).

**Проверено на реальных данных** (по одному файлу каждого формата — docx, pdf, xlsx, png из `Задача 1/`): холодный запуск — 4 документа за 5.4 сек, тёплый (из кэша) — за 0.01 сек, `doc_id` между запусками совпали (подтверждает, что кэш реально сработал, а не просто быстро перепарсил). Результат без ошибок прогнан через `rag_core.retrieve()` — валиден по обеим схемам, найдены релевантные чанки.

CLI:
```bash
python modules/ingestion/ingest.py --folder "путь/к/папке" --cache-dir data/parsed_documents
```

### Результаты прогона на реальных данных задачи (`Задача 1/`)

- **PDF из `Дополнительные материалы/`**: 4 из 5 файлов оказались обычными "цифровыми" PDF с текстовым слоем — извлеклись мгновенно через `pdfplumber`, OCR не понадобился. Только `geokniga_lodeyshchikovvv...zolotaiserebraizupornyh1.pdf` — настоящее фото книги без текстового слоя; OCR отработал с уверенностью **~0.82**, текст читаемый.
- **PNG из `Регламенты/`**: списки оборудования (обычный текст в таблице) распознаются хорошо, уверенность **0.58–0.68**, текст в целом читаемый.
- **PNG из `Схемы флотации/`**: простые блок-схемы с текстовыми подписями (стрелки + названия стадий) распознаются неплохо, уверенность **0.5–0.9**. Схемы с плотными числовыми таблицами и мелким шрифтом (например, `Регламент 1.png`) распознаются **плохо** (уверенность близка к 0 — обычный Tesseract не справляется с сложным layout из мелких таблиц и рамок).
- **xlsx из `Пример 1/Хвосты КГМК.xlsx`**: распознан 1 лист ("Итог", 119 строк), корректно извлечены все ожидаемые по `Как читать отчет института по хвостам.docx` данные — СМТ (сухие метрические тонны), содержание элемента 28 (Ni) и 29 (Cu) в % и тоннах, разбивка по классам крупности (+125, +71, -71+45, -45+20, -20+10, -10), минералогия (раскрытый/закрытый Pnt/Cp, миллерит, пирротин, пирит), извлекаемый/неизвлекаемый металл. Числа с плавающей точкой форматируются до 6 значащих цифр для читаемости. Встречаются ячейки `#REF!` — это битые формулы в самом исходном файле, ingestion передаёт их как есть (не наша ошибка).

**Вывод:** OCR — не проблема для "текстовых" сканов и простых схем, но для плотных технологических таблиц-схем нужен более сильный подход (см. TODO ниже). xlsx-парсинг полностью рабочий на реальных данных задачи.

## OCR: установка Tesseract (системная зависимость)

`pytesseract` — это только Python-обёртка, движок Tesseract нужно ставить отдельно:

- **Windows**: `winget install --id UB-Mannheim.TesseractOCR`
- **GitHub Codespaces / Debian**: `sudo apt-get update && sudo apt-get install -y tesseract-ocr tesseract-ocr-rus`

По умолчанию `pytesseract` ищет `tesseract` в `PATH`. На Windows, если winget-инсталлятор не добавил его в `PATH`, `ingest.py` сам подставляет дефолтный путь `C:\Program Files\Tesseract-OCR\tesseract.exe`.

**Русский языковой пакет**: winget-версия Tesseract по умолчанию ставит только `eng.traineddata`. Если распознавание русского не работает (или `pytesseract.get_languages()` не показывает `rus`):
- Либо переустановите Tesseract с выбором русского языка в мастере установки (нужны права администратора на запись в `Program Files/Tesseract-OCR/tessdata`);
- Либо скачайте `rus.traineddata` (например, с github.com/tesseract-ocr/tessdata_fast) в отдельную папку и укажите её через переменную окружения `TESSDATA_PREFIX` перед запуском (например, `TESSDATA_PREFIX=/path/to/tessdata pytest ...`) — так можно обойтись без прав администратора.

Тесты в `tests/test_ingestion.py`, которым нужен OCR, автоматически пропускаются (`skip`), если Tesseract не найден в системе — так что отсутствие OCR-движка не ломает прогон тестов у тех, кто его ещё не поставил.

## Известный нюанс: pdf с битыми метаданными ширины глифов (авто-исправляется)

На реальном файле `Задача 1/Дополнительные материалы/geokniga-metallurgiya-blagorodnyh-metallov_0.pdf` обнаружили: у некоторых старых pdf (похоже, экспортированных кривым OCR-инструментом ~2007 года) в самом файле битые метаданные ширины символов — у большинства символов на странице `x1 - x0 ≈ 0`. Из-за этого обычная кластеризация `pdfplumber` в слова переставляет буквы местами (например, "цветных" превращается в "ых нтевц"), хотя при ручном копировании текста из PDF-вьюера (Adobe/браузер) текст читается нормально — сам текстовый слой не битый, ломается только автоматическая реконструкция порядка слов.

`_ingest_pdf` теперь **автоматически** определяет такие страницы (доля символов с нулевой шириной глифа ≥ 50%, см. `_ZERO_WIDTH_GLYPH_RATIO_THRESHOLD`) и вместо `page.extract_text()` собирает текст напрямую из `page.chars` в исходном порядке потока pdf, группируя по строкам через координату `top` (`_reconstruct_text_from_chars`) — порядок символов в потоке оказывается корректным, просто его нельзя восстановить через обычную пространственную кластеризацию. Число таких страниц видно в `metadata.extra.raw_char_pages`.

Ограничение: если на одной строке визуально наложены два отдельных текстовых блока (например, декоративная обложка с фоновыми символами Au/Ag под заголовком), группировка по `top` не может их разделить — для контентных страниц (не обложек/дизайнерских элементов) это не проблема, проверено на реальном файле (страницы 4+ распознаются идеально).

## Известный нюанс: Unicode-нормализация имён файлов

Часть файлов в `Задача 1/` (судя по всему, после синхронизации с macOS) хранит кириллические имена в NFD-форме Unicode (например, "й" как разложенные "и" + `U+0306`). Из-за этого ручной ввод такого пути в терминал/скрипт может не найти файл, даже если он визуально выглядит идентично. Обходной путь — не набирать кириллические имена вручную, а получать `Path`-объекты через `Path.iterdir()`/`glob()` и передавать их дальше как есть.

## Рекомендованные библиотеки

- `python-docx` — .docx (уже используется)
- `pdfplumber` — .pdf с текстовым слоем (уже используется)
- `pypdfium2` — рендер страниц pdf в изображение для OCR сканов (уже используется, без системных зависимостей типа poppler)
- `pytesseract` + `Pillow` — OCR png/jpg и pdf-сканов (уже используется, нужен системный Tesseract — см. выше)
- `openpyxl` — .xlsx (уже используется)

## Как тестировать независимо

```bash
# из корня репозитория
pip install -r requirements.txt
pytest modules/ingestion/tests/test_ingestion.py -v

# ручной прогон на своём файле
python modules/ingestion/ingest.py "путь/к/файлу.pdf"
# с ограничением числа страниц (полезно для больших сканов):
python modules/ingestion/ingest.py "путь/к/большому_скану.pdf" --max-pages 3

# пакетная обработка папки с кэшированием
python modules/ingestion/ingest.py --folder "путь/к/папке" --cache-dir data/parsed_documents
```

Тесты в `tests/test_ingestion.py` сами создают временные .docx/.pdf/.png файлы и валидируют результат `ingest()` через `schemas/validate_schema.py` — реальные файлы из `Задача 1/` не обязательны для прогона тестов, но пригодятся для ручной проверки на реальных данных (см. результаты выше).
